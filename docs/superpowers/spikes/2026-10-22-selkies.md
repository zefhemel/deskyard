Can Selkies replace KasmVNC as Deskyard's screen streaming, with sound in sync with the picture? This was a time-boxed spike on branch `claude/selkies-spike-98a338`. The code there is a prototype, not production code.

# Answer

**Recommendation: switch, after a short hardening pass.** Selkies 2.1 streams our X11 XFCE desktop over a single WebSocket, through the supervisor and behind Caddy's token.
- **Sync.** Sound is about 4× closer to the picture than with KasmVNC: +21 ms against +97 ms on a clean network. It stays inside the −45 to +125 ms target on every network tested except single beeps at 150 ± 50 ms (+129 ms worst, against KasmVNC's +165 ms).
- **Lag.** Total sound lag is about half of KasmVNC's.
- **The user's check.** They watched YouTube in the desktop's Chromium and found the sync "works well enough".
- **What it costs:**
  - more CPU while idle with a viewer connected (fixable in part);
  - 177 MB more image;
  - rewriting the desktop page's frame protocol (`kasm.ts`);
  - dropping most of the audio stack being built on `audio-and-ports`.

**Not a hybrid.** Selkies also has no real A/V sync: its stream carries no timestamps, and it plays sound and picture as soon as they arrive. It wins because both paths are short (H.264 frames at 60 fps, Opus in 10 ms frames, a small adaptive jitter buffer), not because of sync logic. So keeping Deskyard's own audio next to Selkies' video would throw away the advantage. Use Selkies' sound.

# 1. X11: supported, the default (no dealbreaker)

- Selkies 2.0 (2026-09-23) and 2.1.0 (2026-10-21) keep X11 as the default backend. Wayland is opt-in (`--wayland` / `SELKIES_WAYLAND`, default false). The 2.0 release notes: "The X11 backend is the default". The 2.1 notes still fix X11-path bugs.
- LinuxServer's base image runs X11 (Xvfb + Openbox) unless `PIXELFLUX_WAYLAND=true`. Their Webtop debian-xfce tag is X11-only.
- LinuxServer uses a patched XLibre Xvfb (GPU pixmap via glamor, RandR-resizable framebuffer). We used **Debian's stock Xvfb**. pixelflux then captures through XShm with one copy per frame (the documented fallback). It worked, including resizes up to the framebuffer we start with (3840x2160).
- **Agent tools, checked in the running desktop:** `deskyard size`, `click`, `type`, `key`, `screenshot`, `zoom` and `xclip`, all on :1. XFCE and Chromium run as before.

# 2. In the image

What changed in `images/debian-xfce/`:
- **Removed:** KasmVNC (`Xkasmvnc`, its web client, `start-xvnc`).
- **Added:**
  - `xvfb x11-xserver-utils xcvt python3 python3-venv`;
  - `pip install selkies==2.1.0` into `/opt/selkies`. The PyPI wheels pull in pixelflux 2.2.1 and pcmflux 2.2.0 as manylinux aarch64 and x86_64 wheels. Selkies' web client ships in the wheel.
- **`start-xvfb`:** `Xvfb :1 -screen 0 3840x2160x24` with RANDR, DAMAGE, XFIXES, XTEST and MIT-SHM, then a `cvt`/`xrandr` mode at `WORKSPACE_RESOLUTION`.
- **`start-selkies`:** `selkies --mode websockets --addr 127.0.0.1 --port 6080` as `user`, with:
  - `SELKIES_ENABLE_BASIC_AUTH=false` (Caddy's token is the auth);
  - `SELKIES_ALLOWED_ORIGINS='*'`: a spike shortcut, because the supervisor rewrites Host;
  - `SELKIES_AUDIO_DEVICE_NAME=deskyard-speaker.monitor`;
  - `SELKIES_UI_SHOW_SIDEBAR=false`;
  - `SELKIES_MICROPHONE_ENABLED=true`;
  - `SELKIES_USE_CSS_SCALING=true` (see "HiDPI" below);
  - `SELKIES_USE_BROWSER_CURSORS=false`: the page draws the pointer (see "Pointer offset" under Smoothness).
- **Caddy:** unchanged. The default route still proxies to 127.0.0.1:6080 after the `X-Deskyard-Token` check. Nothing new runs as root, and no new ports.
- **Healthcheck:** `/api/health` on 6080.

**HiDPI.** By default Selkies sizes the screen in device pixels. On a Retina Mac that gave a 2296x1456 screen at 192 DPI: XFCE scales the text but not the panel or dock, which looked tiny (the user noticed at once). With `SELKIES_USE_CSS_SCALING=true` the screen is in CSS pixels at 96 DPI, as with KasmVNC, and the browser scales it up (a little soft on Retina, as before). A sharp 2× mode would need XFCE window scaling, and agents' coordinates would double.

# 3. Through the supervisor

- **Proxy.** `/<name>/selkies/…` is proxied to the desktop's Caddy at `/…`: HTTP and the `/api/websockets` WebSocket, with the desktop token and no cookie (`proxySelkies` in `supervisor/internal/server/desktop.go`). The WebSocket counts as viewing, so avatars and join toasts work.
- **Frame.** The desktop page frames `/<name>/selkies/`. Selkies derives its WebSocket URL from the page's folder, so no subfolder setting is needed.
- **Hack:** for the measurements, the supervisor injects an audio tap into Selkies' `index.html` and drops Selkies' CSP header. It would not survive.
- **`?kasm=1`** shows KasmVNC on a KasmVNC image again, for comparisons.

# 4. Measurements

**Setup.**
- OrbStack on a MacBook Air (arm64), Playwright Chromium, 60 s per run.
- The A/V test page runs in the desktop's Chromium, with the `?avsync=1` readout. The readout reads flashes from Selkies' `<video>` and beeps from the tap.
- **Fake audio output** (`--disable-audio-output`, outputLatency 16 ms) for every run, so nothing was audible. The real default output here reported 192 ms (a Bluetooth device, as in the earlier AirPods note).
- **KasmVNC re-measured** the same way, from the pre-spike commit `e3f3684`. It matches the numbers in the [[superpowers/plans/2026-10-22-audio-and-ports|Audio and ports plan]]: +97 ms against +103 ms, and 112 ms against 116 ms lag.

**Lag.**
- **Selkies has no capture timestamps.** The test page got an `?epoch=1` mode instead: it beeps and flashes on whole wall-clock seconds, and lag = when it is heard or seen in the browser − that second. That assumes synced clocks; the container's clock was measured within about 15 ms of the Mac's.
- **The two lags aren't the same measure.** Selkies' sound lag includes the desktop Chromium's own output to PipeWire. KasmVNC's (the Player's) starts at the capture. So Selkies' lag is the stricter of the two.
- **Offset** is sound − picture, measured on the browser's clock alone.

All times are in ms, as median / worst.

| Network | Selkies offset | KasmVNC offset | Selkies sound lag | KasmVNC sound lag | Selkies picture lag |
| --- | --- | --- | --- | --- | --- |
| Clean | **+21** / +59 | +97 / +111 | **60** / 84 | 112 / 121 | 41 / 58 |
| 60 ± 20 ms each way | **+44** / +89 | +86 / +136 | **147** / 321 | 175 / 186 | 103 / 236 |
| 150 ± 50 ms each way | **+58** / +129 | +85 / +165 * | **259** / 346 | 278 / 293 * | 204 / 262 |
| 2 Mbit/s cap | **+26** / +38 | +103 / +230 * | **76** / 98 | 116 / 288 * | 47 / 63 |
| 1 Mbit/s cap | **+31** / +50 | +100 / +294 | **103** / 441 † | 115 / 292 | 66 / 466 † |
| 500 ms stall every 10.37 s | **+25** / +49 | +97 / +122 * | **50** / 103 | 120 / 145 * | 22 / 71 |

\* from the plan's Status section (not re-run). † the first beep after connecting; afterwards ≤ 127 ms.

- **Delay and jitter.** The offset stays inside the target except single beeps at 150 ± 50 (+129 ms). Selkies has no fixed audio buffer to absorb jitter: its jitter buffer adapts, and the picture shows frames on arrival. So jitter shows up a little in the offset, and one 60 ± 20 burst reached 321 ms lag for two beeps.
- **Bandwidth caps.** Selkies' congestion control lowers the video bitrate (CBR 8 Mbit/s by default), so sound no longer queues behind frames, unlike KasmVNC. Lost beeps: 4 of 67 at 2 Mbit/s, 9 at 1 Mbit/s.
- **Stalls.** A beep caught in a stall is dropped (the worklet's drop-oldest ceiling) instead of played late. 3 of 60 beeps were missing and the next beep was back in range. The first stall run, every 10.0 s, lined up with the 1 s beeps and never hit one, so it was re-run with a 10.37 s period.

**Smoothness.**
- **Measured:** Selkies' client reported a steady 60 fps (Turbo mode) while a 720p30 test video played full-screen in the desktop's Chromium, and 30 fps with Turbo off (matching the video's 30 fps).
- **Subjective:** the user watched YouTube on a Selkies desktop and judged the sync acceptable.
- **Pointer offset while dragging a window (fixed, two causes).** In Chrome on a Retina Mac, the user saw the drag pointer sit some pixels above where they pressed, snapping back on release.
  - **Inside our frame (the real cause).** Chrome reports `pointerrawupdate` coordinates relative to the top-level page, not the iframe: clientY 546 against `pointermove`'s 500, which is our 46 px bar. Selkies sends motion from `pointerrawupdate` while a button is held (it fires only in secure contexts, localhost included) and skips the duplicate `pointermove`. So drags went to the desktop 46 px too low, while press and release used the right coordinates. The spike hides `pointerrawupdate` from Selkies' page in the injected script (deletes `onpointerrawupdate` and drops listeners for it), and Selkies falls back to `pointermove`. The page is served `no-store`, because a cached copy (a 304) skipped the injection in the user's Chrome at first. Verified with `?ptrdebug=1`, a readout on our page: the X pointer now matches the frame position while hovering and dragging, and the user confirmed dragging is right in their Chrome. For real: report it upstream (Selkies, or Chromium if it's Chrome's bug), or keep a small shim, or put our bar inside the same document.
  - **Opened directly, without our frame.** As a CSS cursor, real Chrome seemed to misplace the hotspot of centred pointers such as the move pointer. `SELKIES_USE_BROWSER_CURSORS=false` (the page draws the pointer) fixed it for the user.

**CPU** (`docker stats`, % of one core; video = a 720p30 VP9 test video full-screen in the desktop's Chromium, 1280x800):

| | No viewer | Viewer, idle desktop | Viewer, video playing |
| --- | --- | --- | --- |
| KasmVNC | 0.0 | 0.1 | 47 |
| Selkies, default (Turbo: encodes every frame at 60 fps) | 1.5 | 40 | 65 |
| Selkies, `SELKIES_VIDEO_STREAMING_MODE=false` | 0.9 | 12.5 (Xvfb 7, Selkies 4) | 54 |

Encoding is CPU x264, since there's no GPU here. Idle with a viewer stays well above KasmVNC even with Turbo off. Find out what keeps Xvfb busy (pixelflux polling damage?) before shipping.

**Image size:** 2.31 GB → 2.49 GB, +177 MB (+7.6 %). The Selkies venv alone is 158 MB: pixelflux and pcmflux with their libs, Pillow, cryptography, uvloop, pip. Some of that could be trimmed (pip, the WebRTC dependencies).

# 5. Features

| Feature | Works | Notes |
| --- | --- | --- |
| Clipboard both ways, from our bar | Yes | Same-origin frame. Our page posts `{type: "clipboardUpdateFromUI", text}` to `frame.contentWindow` and it lands in the desktop (checked with `xclip -o`). The desktop's clipboard comes back as `{type: "clipboardContentUpdate", text}`, posted on the frame's own window, not the parent, so we listen on `frame.contentWindow`. Images and seamless clipboard exist too (`SELKIES_ENABLE_BINARY_CLIPBOARD`, `SELKIES_CLIPBOARD_SEAMLESS`). |
| Several viewers at once | Yes, with a bug | **Bug:** if a tab of the desktop goes into the background while it's the only viewer, its client sends `STOP_VIDEO` and Selkies stops the display's stream. A viewer who joins after that sits on "Waiting for stream…" until Selkies restarts (reproduced). While two viewers are already connected, a hidden tab only pauses itself. New in 2.1: a second tab joins beside the first instead of evicting it, and both control. The first viewer's window sets the screen size; a smaller second viewer gets the picture letterboxed to fit. The supervisor saw both WebSockets as viewers. |
| Resize to the browser window | Yes | 1280x846 → 1100x746 viewport gave a 1100x700 screen, and back. |
| Scale-to-fit ("Lock size") | Yes | `setManualResolution {width, height}` + `setScaleLocally true` kept 1280x800 while the window shrank, scaled to fit. `resetResolutionToWindow` undoes it. |
| Quality and bitrate | Yes | `{type: "settings", settings: {video_bitrate, framerate, encoder, …}}` applies live ("Applying video settings … live (no restart)"). Ranges and locks come from `SELKIES_*` settings; locked settings vanish from Selkies' own UI. We'd map Low…Lossless to bitrate/CRF/encoder (`jpeg` and `h264enc-striped` exist too). |
| Mic from the browser | Yes | `{type: "pipelineControl", pipeline: "microphone", enabled: true}`. Selkies adds its own `input` null sink and a `SelkiesVirtualMic` source, played at 24 kHz mono and removed when the viewer leaves. That is a second virtual mic next to our `deskyard-mic`: pick one. Per-viewer mic badges would need the supervisor to see it (it's inside the one WebSocket). |
| Keyboard and layout | Yes | Typed `echo kb-ok é ü € @` from the browser into a terminal and got exactly that. Keys travel as keysyms, so the browser's layout decides the characters. Ctrl+Shift+T reached the app. Selkies keeps Ctrl+Shift+F/M/X/G for itself unless `SELKIES_KEYBOARD_SHORTCUTS=false`, which we'd set. Our Keys menu (server-side xdotool) is unaffected. |
| Reconnect after a desktop restart | Yes | Upgrading (recreating) the `watch` desktop while the user had it open: the page reconnected by itself and resized the new screen to its window. Our bar's connection dot needs a new source, because Selkies posts no `connection_state`. |

# What Deskyard would have to rebuild

- **Image:**
  - Xvfb and Selkies instead of KasmVNC (done here);
  - a proper Origin setting instead of `*`;
  - `SELKIES_KEYBOARD_SHORTCUTS=false`, Turbo off;
  - turn off what Deskyard doesn't offer, or decide on it: file transfers (`SELKIES_FILE_TRANSFERS`, upload to `~/Desktop` and download for anyone viewing), printing, gamepads, webcam, `/api/screenshot`, sharing links;
  - one virtual mic;
  - pin and verify the wheels.
- **Supervisor:**
  - `/<name>/selkies/*` replaces `/<name>/websockify` and the KasmVNC client-file extraction (`clientFiles`);
  - no HTML injection;
  - decide which Selkies HTTP APIs to pass through (today all of `/api/*`);
  - the audio hub and `/<name>/audio` (contract 2) become unnecessary for playback;
  - something in place of the injected shim that hides `pointerrawupdate` in the frame (see "Pointer offset").
- **Desktop page:**
  - `kasm.ts` becomes a Selkies adapter: clipboard, quality, Lock size, volume/mute (`setVolume`, `setMute`), sound on/off (`pipelineControl audio`), mic, focus and the connection state;
  - the Audio panel drives Selkies instead of our Player;
  - the `?avsync=1` readout keeps the Selkies variant (`startSelkiesAvSync`), and needs a cleaner tap than injection;
  - a sound and mic design that fits Selkies (e.g. mic badges from the client's `pipelineStatusUpdate` reported to the supervisor).
- **Tests:** `images/debian-xfce/tests/test_web.py` and the supervisor's UI tests assume KasmVNC.
- **The audio-and-ports branch:** audio-serve, the hub, the Player and its AudioWorklet are superseded by Selkies' sound. The spec's sync targets, Lock size and port mapping stay.

# Risks

- **Young and fast-moving.** 2.0 is a month old and 2.1 a day old, with big rewrites (GStreamer dropped for pixelflux/pcmflux). Expect breaking changes; pin versions.
- **Idle CPU.** 12–40 % of a core per desktop with a viewer, against ~0 for KasmVNC. That matters for many desktops on one host.
- **No real A/V sync.** The good numbers come from low latency on both paths. Under heavy jitter (150 ± 50 ms) single beeps leave the target. The stream has no timestamps, so we can't add sync ourselves without patching Selkies.
- **Stock Xvfb.** LinuxServer patches Xvfb (resizable framebuffer, GPU pixmaps); we rely on a fixed 3840x2160 framebuffer and the XShm copy path. Larger browser windows can't grow past it.
- **Security surface.** Selkies has more endpoints than KasmVNC: file transfer, printing, apps, sharing tokens, metrics and screenshots. They're behind Caddy's token and the supervisor's session, but every viewer gets all of them unless we turn them off.
- **HiDPI** is soft (CSS scaling), as with KasmVNC. Sharp 2× would need XFCE scaling and changes agent coordinates.
- **Firefox and Safari** weren't measured. Selkies uses WebCodecs, with a `MediaStreamTrackGenerator` `<video>` on Chromium and canvas elsewhere, so their numbers may differ.
- **Not checked:** smoothness on a slow real network, long sessions, many viewers on several desktops.
