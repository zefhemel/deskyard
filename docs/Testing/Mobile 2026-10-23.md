Partial mobile assessment of the running local Deskyard instance at `http://localhost:8080`. The initial pass found two responsive-layout issues in desktop Chrome. A follow-up reached live desktops on iPhone and iPad through Device Hub and verified iPad terminal input and special keys. Full touch and Android interaction testing remains incomplete; these results are not device compatibility certification.

# Fix follow-up in the mobile-controls worktree
The toolbar now moves Lock size, Keys, Quality and Download into More below 1024 CSS pixels, including narrow tablets and phone landscape. Its action group does not shrink out of view. Menus measure the space below their trigger against the visual viewport, scroll within that space, and update when the viewport resizes or scrolls. The tests cover 390×760, 744×1133, 874×402 and 375×600, then shrink each already-open menu to a 400-pixel-high viewport and reach Download.

Clipboard now retains its draft on a window blur that does not focus the remote frame. An actual pointer/touch interaction inside the frame dismisses it, even when Selkies prevents the browser's normal focus change. Chromium and WebKit touch-context tests retained the draft, sent it to the real desktop's X clipboard, and dismissed the panel with a screen tap. This addresses the reproduced focus loss; it does not establish the cause of the original simulator's intermittent clipboard-delivery failure.

The existing live window-drag regression now also sends touch input. Both mouse and touch moved the terminal. Selkies consumes the initial small movement while distinguishing a drag from a tap, so the touch test allows up to 15 remote pixels of that movement. No touch-input implementation change was made. This browser check supersedes the earlier absence of a successful touch drag, while Device Hub and physical-device confirmation remain outstanding.

Direct software-keyboard entry into the streamed desktop, two-finger scrolling, the single Safari reload and Android's Chrome ANR remain outside the verified fixes. No restart or replacement of the existing localhost:8080 supervisor was needed; integration tests used separate supervisors, disposable desktops and subnet pools.

This happened once; its cause and reproducibility are not established. Do not attribute it conclusively to Deskyard, rotation or input without reproducing it and checking simulator/browser diagnostics.

The pink Selkies keyboard control was visible while connecting on both Apple devices but was no longer visible in the connected screen during these checks. Inspection of the cached client's frontend showed that this button is conditional on its attached-input detection; hardware key presses and a fine pointer can mark input as attached. Direct software-keyboard entry into the streamed desktop and two-finger scrolling remain unverified.

## Intermittent iPad Clipboard input and delivery
With the live desktop connected, opened Clipboard and tapped inside “Send to zef.” The popover disappeared on two attempts. A later attempt kept focus and displayed the software keyboard; tapping A inserted `A`. Tapping the blue “Paste into zef” button closed the panel, but reopening it still showed the previous remote clipboard contents, and Terminal → Edit → Paste inserted that previous text rather than `A`. This is a failed end-to-end clipboard delivery check, with intermittent focus behavior; the cause is not established and should be reproduced outside automation before attributing it conclusively to the product. # Reproduced layout issues

## Tablet toolbar clips its More control
Open `/zef/` at 744×1133. The full desktop toolbar remains visible at this width, squeezes the desktop name out, and places the More button partly beyond the right edge. Its measured horizontal bounds were approximately 723–757 CSS pixels in a 744-pixel viewport. This reduces access to the desktop's actions on an iPad mini sized portrait layout. The toolbar fits at the tested 874-pixel landscape width.

The source uses the `sm` breakpoint to hide the full controls and move actions into More, although the full bar needs more space at the tested tablet width. See `supervisor/web/src/desktop/desktop.tsx` and [[Architecture/Web UI]].

![Tablet toolbar clips the desktop name and More button](Mobile%202026-10-23/tablet-toolbar.jpg)

## Short phone viewport clips the More menu
Open `/zef/` at 375×600 and open More. The menu extends below the screen: in this run its top was approximately 44 pixels and its bottom approximately 698 pixels. Lower quality choices and Download cannot be reached visually; the menu has `overflow-y: visible` rather than its own scroll area. The tested 360×800 portrait viewport had room for the menu while disconnected from the screen; a connected display owner can have an additional Lock size entry.

The shared menu in `supervisor/web/src/components/menu.tsx` has no viewport-height bound or scroll area. Recheck this menu with a connected desktop and a visible mobile keyboard after changing it.

![Short phone viewport clips the lower menu actions](Mobile%202026-10-23/phone-menu-clipped.jpg)

# Screen connection blocker
The normal `/zef/` page repeatedly remained blank at Connecting at phone, tablet and 1280×900 desktop sizes, including after a reload. The embedded iframe had the expected URL `/zef/screen/` and occupied the available screen area, but inspection returned no body text. Opening `/zef/screen/` directly in a separate tab produced a live XFCE/Chromium picture. The direct client logged a warning that initial-mode detection returned HTTP 404, but still showed the picture.

This was not isolated to mobile and its root cause was not established. Treat it as a local test blocker requiring investigation, not a confirmed mobile-specific rendering defect. No restart or configuration change was made to the user's desktop to work around it.
